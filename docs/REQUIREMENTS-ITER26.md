## 0. 背景与动机

E2E Chrome 测试经 R211→R288 九次迭代稳定化后，R299 扩展至 6 条路径（3 条冒烟 + 3 条核心场景）。但现有 6 条路径均为**单功能冒烟验证**（扩展加载、SidePanel 渲染、选中文字气泡、书签 UI 结构、知识库列表、设置主题切换），不覆盖任何**跨模块完整用户路径**。

用户使用 PageWise 的核心价值在于**端到端闭环**：选中文字 → 获得 AI 回答 → 保存到知识库 → 日后搜索回顾。当前 E2E 完全不验证这条闭环。同理，书签知识图谱路径（采集 → 搜索 → 推荐 → 可视化）和学习闭环路径（复习 → 打卡 → 教练回顾）是产品差异化竞争力的体现，也无 E2E 覆盖。

**R288 的"未来扩展指引"（第 8 节）明确建议：冒烟稳定后扩展至书签搜索/知识库查询等深层路径。** R312 是这一指引的落地执行。

### 现有 6 条路径概览

| # | 路径 | 类型 | 超时 | 来源 |
|---|------|------|------|------|
| P1 | 扩展加载 → SW 激活 | 冒烟 | 30s | R288 |
| P2 | SidePanel → 渲染 UI | 冒烟 | 30s | R288 |
| P3 | 选中文字 → 气泡弹出 | 冒烟 | 30s | R288 |
| P4 | 书签面板 UI 结构渲染 | 冒烟 | 45s | R299 |
| P5 | 知识库搜索 → 结果列表 | 冒烟 | 45s | R299 |
| P6 | 设置页 → 主题切换 | 冒烟 | 45s | R299 |

## 1. 用户故事

### US-1: 选中即问完整闭环

> 作为一名技术开发者，我希望选中网页上的技术概念后，能直接获得 AI 解释，并自动归档到本地知识库，之后能通过关键词搜索找到这条归档记录。这样我的阅读学习成果不会丢失，且随时可回顾。

### US-2: 书签知识图谱探索

> 作为一名收藏了大量技术文章的开发者，我希望基于已有书签自动发现相关联的内容，通过语义搜索快速定位目标，并在知识图谱中直观看到书签之间的关联关系，从而建立结构化的知识体系。

### US-3: 学习闭环与复习

> 作为一名学习新技术的开发者，我希望对已归档的知识进行间隔复习，通过自评打分加深记忆，并结合学习目标打卡和学习教练的回顾建议，形成完整的学习闭环，确保学到的知识真正内化。

## 2. 验收标准

### AC-1: 新增 3 条深度用户路径全部通过

在 `tests/e2e-chrome/` 中新增测试文件（或追加至 `test-core-scenarios.js`），包含以下 3 条路径，`npm run test:e2e` 中 ≥9 条路径通过（原有 6 条 + 新增 3 条）。

**路径 7: 选中文字 → AI 问答 → 知识库归档 → 搜索验证**

```
1. 创建包含技术内容的测试页面
2. 选中文字 → 验证 toolbar 气泡弹出 (复用 P3 前置)
3. 点击 AI 问答按钮 → 侧边栏打开并显示对话区
4. 模拟 AI 回答完成 → 验证对话面板中出现回答内容
5. 触发"保存到知识库"操作 → 验证归档操作执行
6. 打开知识库面板 → 搜索关键词 → 验证搜索结果中包含归档条目
```

**路径级断言（最终状态）**:
- 知识库搜索结果中存在至少 1 条与归档内容相关的条目
- 归档条目包含标题/来源 URL/标签等必要字段

**路径 8: 书签采集 → 语义搜索 → 相似推荐 → 图谱可视化**

```
1. 打开书签面板 → 验证书签列表渲染
2. 在书签搜索框中输入语义查询关键词
3. 验证搜索结果列表非空
4. 点击搜索结果中某个书签条目 → 验证书签详情面板打开
5. 验证详情面板中存在"相似书签"推荐区域
6. 点击"完整图谱"按钮 → 验证图谱可视化界面渲染
```

**路径级断言（最终状态）**:
- 书签详情面板展示内容（标题/URL/相似书签列表非空或至少有结构容器）
- 图谱可视化界面渲染完成（Canvas 或 SVG 元素存在）

**路径 9: 间隔复习 → 评分 → 学习目标打卡 → 学习教练回顾**

```
1. 打开学习/复习面板 → 导航至复习 Tab
2. 验证复习队列区域渲染（即使无待复习项，容器应存在）
3. 模拟复习卡片交互 → 选择评分等级
4. 验证评分状态更新
5. 导航至学习目标 Tab → 验证目标面板渲染
6. 触发打卡操作 → 验证打卡状态
7. 导航至学习教练 Tab → 验证教练回顾面板渲染
```

**路径级断言（最终状态）**:
- 学习教练回顾面板包含至少 1 个结构化区域（计划/建议/统计）
- 复习评分后卡片状态从"待复习"变更为"已复习"

### AC-2: 路径级断言策略（非步骤级冒烟）

- 每条新路径仅验证**最终状态**，不验证中间 DOM 过渡状态
- 中间步骤使用 `waitForSelector` / `waitForFunction` 确保页面就绪，但不断言具体属性值
- 断言集中于：(a) 最终面板/容器存在且非空，(b) 数据已写入（知识库归档条目 / 搜索返回结果 / 复习卡片状态更新）
- 目的：降低脆弱性，避免 R211 以来 28% 选择器不匹配失败模式

### AC-3: 超时与重试策略一致

- 每条新路径 **60s 硬超时**（深度路径涉及 AI 调用/知识库写入/搜索，比冒烟路径需要更长时间）
- **2 次自动重试**（仅 TimeoutError），与 R288 策略完全一致
- 重试间隔 1s，让浏览器资源释放
- 非 TimeoutError（如断言失败、元素未找到）直接抛出，不做重试

### AC-4: 串行执行无状态污染

- 所有 9 条路径在同一个 `describe` 块中串行执行
- `--test-concurrency=1` 确保浏览器实例间无状态污染
- 新路径依赖路径 1（扩展加载）作为前置条件，共享 `context` 和 `extensionId`
- 每条路径在 `finally` 块中关闭新打开的页面，避免标签页累积

### AC-5: E2E 基线报告更新

更新 `docs/reports/e2e-baseline.md`，新增以下内容：
- 路径 7/8/9 描述、超时配置、断言策略
- 与 R288/R299 的策略对比（冒烟 vs 深度路径）
- 预期稳定性数据：60s 超时意味着 CI 单条路径最大耗时 60s × 3 = 180s（含重试），9 条路径理论最大 300s，实际预估 ~180s
- 失败模式预期分析：路径 7 涉及 AI mock 响应（最大风险点）、路径 8/9 仅 UI 交互（与现有路径风险一致）

## 3. 技术约束

### 3.1 AI 响应 Mock 策略

路径 7（选中文字 → AI 问答）涉及 AI API 调用，**E2E 测试不应依赖真实 AI 服务**：
- **方案 A（推荐）**: 通过 Service Worker 消息拦截，注入 mock AI 响应（复用 `tests/helpers/e2e-helper.js` 中的 mock 框架）
- **方案 B（兜底）**: 直接通过 `page.evaluate` 写入 IndexedDB 模拟归档结果，跳过 AI 调用
- 无论采用哪种方案，**路径级断言必须验证最终状态**（知识库中有条目），不能因 mock 方式降低验证深度

### 3.2 稳定选择器约束

继承 R288 原则，新路径优先使用以下稳定选择器：
- `#app`, `#panelChat`, `#panelBookmarks`, `#panelKnowledge`, `#panelSettings` — 面板容器
- `.pagewise-toolbar--visible`, `.pagewise-toolbar-btn` — 选中文字气泡
- `#bookmarksList`, `#bookmarksSearchInput`, `#bookmarksDetail` — 书签面板
- `#knowledgeSearchInput`, `#knowledgeResults` — 知识库面板

**禁止**使用：(a) 动态生成的 class/id（如 `.btn-abc123`），(b) 与迭代相关的版本标识，(c) 仅在特定数据状态下存在的选择器

### 3.3 无真实数据约束

E2E 使用全新 Chrome profile（`cleanProfileDir()`），无真实书签/知识库数据：
- 路径 8（书签图谱）的搜索/推荐结果可能为空，断言应验证 UI 结构存在而非结果非空
- 路径 9（学习闭环）的复习队列可能为空，断言应验证面板容器和交互元素存在
- 路径 7（知识库归档）通过测试流程中的操作产生数据，断言可验证数据存在

### 3.4 超时预算约束

| 路径 | 硬超时 | 重试 | 最大耗时 |
|------|--------|------|----------|
| P1-P3 (冒烟) | 30s | 2 | 90s × 3 = 270s |
| P4-P6 (核心场景) | 45s | 2 | 135s × 3 = 405s |
| P7-P9 (深度路径) | 60s | 2 | 180s × 3 = 540s |
| **总计（理论最大）** | | | **1215s (~20min)** |
| **实际预估（正常执行）** | | | **~180-240s (3-4min)** |

- 若实际执行 >5min，需评估是否将冒烟路径（P1-P3）和深度路径（P7-P9）分离为不同 `npm run` 命令

### 3.5 兼容性约束

- 新增代码不得修改 `tests/e2e-chrome/helpers.js` 已有导出（仅可新增）
- 不得修改 `test-smoke.js` 或 `test-core-scenarios.js` 中已有路径（仅可新增路径追加或新建文件）
- `package.json` 的 `test:e2e` 脚本入口不得改变（应自动包含新文件）

## 5. 非目标（明确排除）

1. **不新增独立 AI API 测试** — AI 功能已有独立 E2E 文件（`test-ai-client-e2e.js` / `test-ai-cache-e2e.js`），R312 仅在用户路径上下文中验证集成
2. **不修改测试基础设施** — `helpers.js`、重试机制、CI workflow 保持不变
3. **不追求覆盖率提升** — R312 是浏览器 E2E 测试，不影响 c8 代码覆盖率统计
4. **不新增 10 条以上路径** — 精准覆盖 3 条核心闭环路径，避免 R211 的"42 条路径→60% CI 稳定率"陷阱
